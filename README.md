# Urban Mobility Service & Accessibility Optimization

> Business Analyst case study combining Chennai Metro passenger demand with GTFS-based network, scheduled travel-time and first/last-mile evidence.

## 🔴 Live Dashboard

### 🚀 [Open the Interactive Dashboard](https://sanjay-arlo.github.io/urban-mobility-service-accessibility-analysis/)

The dashboard loads repository CSV outputs directly. Ridership and ticketing are based on CMRL passenger-flow reporting; station, first-mile and scheduled-segment metrics are generated by the automated GTFS refresh pipeline.

## 🎯 Business Problem

Transport-planning teams need a repeatable way to understand demand patterns and network-access signals before prioritising deeper operational studies.

**Business Question → Data → Validation → KPI → Segmentation → Insight → Recommendation**

## Business Questions

1. How has Chennai Metro passenger demand changed month by month?
2. Which periods show the strongest observed ridership?
3. How has the mix of NCMC, QR and closed-loop ticketing changed?
4. Which stations show stronger network connectivity?
5. Which stations are farther from the nearest bus stop?
6. What scheduled travel-time evidence is available between adjacent metro stops?
7. Which stations or network patterns deserve deeper first/last-mile investigation?

## 🧮 KPI Definitions

### Ridership
`Total Ridership = SUM(monthly total_ridership)`

### Weighted ticketing share
`NCMC Share = SUM(NCMC) / SUM(Total Ridership)`

This avoids averaging monthly percentages without weighting by passenger volume.

### MoM growth
`MoM Growth % = (Current Month Ridership − Previous Month Ridership) / Previous Month Ridership × 100`

### Scheduled travel time
For adjacent metro-stop pairs present in the CMRL GTFS schedule, scheduled travel time is derived from `stop_times.txt`. The dashboard reports the median scheduled duration across matching trip records. This is **timetable evidence**, not observed congestion or real-world travel time.

### First/last-mile proximity
For each coordinate-valid CMRL stop:

- `Nearest bus stop distance` = straight-line Haversine distance to the closest MTC GTFS bus stop.
- `Bus stops within 500m` = number of MTC GTFS bus stops inside a 500m straight-line radius.

### Network + first-mile screening index
A transparent 0–100 analytical index combines three min-max-normalised components with equal weight:

1. Metro route coverage
2. Inverse nearest-bus-stop distance
3. Bus-stop density within 500m

It is a **screening index only**. It is not a measure of transport equity, socioeconomic accessibility, observed travel time, pedestrian accessibility or service quality.

## ⚠️ Data Integrity

Passenger-flow figures are based on CMRL passenger-flow reporting stored in `data/cmrl_passenger_flow.csv`.

The automated GTFS pipeline uses separate community-maintained **CMRL** and **MTC** static feeds from the ChennaiGTFS project. They are used because they expose machine-readable network structure for this portfolio workflow; they are **not presented as official CMRL/CUMTA publications**.

Static GTFS provides scheduled transit information. It does not prove real-time delays or actual road congestion. Straight-line first-mile distance is a geographic proximity measure, not pedestrian-network walking distance.

The model deliberately keeps monthly ridership, station-level metrics and segment-level travel time at separate grains to avoid misleading joins and inflated passenger totals.

## 🔄 GTFS Refresh Pipeline

`python scripts/build_gtfs_accessibility.py` downloads separate CMRL and MTC GTFS feeds and generates:

```text
data/
├── gtfs_station_metrics.csv
├── gtfs_metro_segment_travel_times.csv
└── gtfs_refresh_metadata.json
```

GitHub Actions runs the refresh weekly and also supports manual execution through workflow dispatch.

The pipeline:

1. downloads separate CMRL and MTC GTFS feeds;
2. preserves all coordinate-valid CMRL stops for station coverage;
3. maps scheduled CMRL route and trip evidence where available;
4. derives median scheduled travel time between consecutive stops;
5. calculates nearest MTC bus-stop distance and 500m bus-stop density using Haversine distance;
6. builds a transparent screening index; and
7. records source, refresh time, coverage counts and limitations in metadata.

The dashboard uses cache-busting query parameters so a previously cached 404 for refreshed CSV outputs does not persist indefinitely in the browser.

```text
    from_stop_id
    to_stop_id
    from_station
    to_station
    median_scheduled_travel_time_min
    trip_observations
```

Monthly ridership should not be directly joined to station-level or segment-level records for passenger totals because the grains are different.
